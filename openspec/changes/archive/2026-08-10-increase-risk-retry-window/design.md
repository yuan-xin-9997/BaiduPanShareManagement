## Context

`get_share_download_url` 方法在获取分享文件下载链接时，如果百度返回风控响应（errno=0 但 list 为非 JSON 数组的密文字符串），会在请求内重试若干次等待恢复。当前重试策略为 4 次，总等待时间约 35 秒。该策略在部分场景下过于保守，容易在风控即将恢复时提前放弃，导致任务进入 6 小时 STANDARD 退避。

## Decisions

### 1. 扩大风控密文重试窗口

将 `risk_retries` 从 4 提升至 8，使总等待时间从 ~35 秒延长至 ~21 分钟。

**计算明细：**

| 重试次数 | 累计等待时间 |
|---------|-------------|
| 1 | 5s |
| 2 | 5s + 10s = 15s |
| 3 | 5s + 10s + 20s = 35s |
| 4 | 5s + 10s + 20s + 40s = 75s |
| 5 | 5s + 10s + 20s + 40s + 80s = 155s |
| 6 | 5s + 10s + 20s + 40s + 80s + 160s = 315s (~5min) |
| 7 | 5s + 10s + 20s + 40s + 80s + 160s + 320s = 635s (~10min) |
| 8 | 5s + 10s + 20s + 40s + 80s + 160s + 320s + 640s = 1275s (~21min) |

**为什么选择 8 次：**
- 总等待 ~21 分钟，比 STANDARD 退避（6h）短很多，不会过度占用任务调度资源。
- 间隔采用指数增长（乘以 2），前期快速重试（5s/10s），后期加大间隔（320s/640s）等待持久性风控恢复。
- 保留当前的设计原则：4 次失败后抛出 `-1`（STANDARD 退避），而非 `-65`（RISK 退避）。

### 2. 保持 -1 错误码不变

风控密文重试耗尽后仍抛出 `-1`（STANDARD 退避，上限 6h），而非 `-65`（RISK 退避，上限 24h）。原因是：
- 密文响应是间歇性抖动的特征，而非硬性封禁，较短退避能给下一次定时同步更多机会。
- 避免被历史失败计数累积压到 24h。

### 3. 退避策略保持不变

- STANDARD 退避：初始 5 分钟，每次失败翻倍，上限 6 小时。
- RISK 退避（errno=-65）：初始 6 小时，每次失败翻倍，上限 24 小时。

## Risks / Trade-offs

- [增加单次请求耗时] → 最坏情况增加约 21 分钟等待，但相比 6 小时退避窗口，该开销可接受。
- [可能让短暂风控恢复变慢] → 前期间隔仍较短（5s/10s/20s），大部分场景在前几次重试即可恢复。
