## Context

同步流程目前通过 `SyncManager` 返回 `files_added` 和 `files_updated`，但这些结果只被汇总成 `sync_runs.message`，没有保存逐文件记录。进程内 `TaskState` 与持久化 `sync_runs` 也没有稳定关联，`/api/state` 会把最近 100 个进程内任务（包括完成和失败任务）全部作为“当前任务”返回。

本次变更跨越 SQLite、同步执行、后台任务、FastAPI 和 Vue 页面。实现必须继续使用现有 Python/FastAPI、Vue 3 和 SQLite 架构，接口必须复用现有页面权限校验，时间必须按北京时间显示。

## Goals / Non-Goals

**Goals:**

- 在文件成功新增或更新到本地后，持久化可按同步映射和单次同步运行追溯的逐文件记录。
- 为进程内同步任务建立到持久化同步运行记录的关联。
- 让“当前任务”只展示 `queued` 或 `running` 状态的任务。
- 提供统一、安全、可排序的文件查询接口和前端弹窗，供同步映射、当前任务、同步历史复用。
- 通过幂等 SQLite 迁移兼容已有数据库和历史记录。

**Non-Goals:**

- 不扫描或开放任意本地目录，也不提供文件下载、预览、删除或编辑能力。
- 不为本次变更引入 PostgreSQL、MySQL 或新的外部依赖。
- 不回填变更部署前各次同步的逐文件历史；旧记录允许显示“暂无文件记录”。
- 不改变同步策略、调度频率或百度网盘下载行为。

## Decisions

### 1. 使用追加式 `sync_file_events` 保存逐次同步结果

新增表保存 `id`、`mapping_id`、`run_id`、`relative_path`、`file_name`、`action` 和 `synced_at`，其中 `action` 至少区分 `added` 与 `updated`。每个成功落地的新增或更新文件对应一条事件，并为映射、运行和排序字段建立索引。

按同步运行查询时直接返回该运行的事件；按映射查询时按相对路径选择最新事件，从而展示该映射目前已同步过的文件且避免同一文件因多次更新重复出现。相比仅在 `sync_runs` 保存 JSON，此结构可索引、可排序、可单独测试，也不会让历史行无限膨胀。相比只维护一张“最新文件”表，追加事件能保留每次运行的准确文件清单。

### 2. 由任务编排层在同步成功后原子记录结果关联

`SyncManager` 继续负责下载并返回 `SyncResult`；`TaskManager` 在获得结果后，以已经创建的 `run_id` 将 `files_added` 和 `files_updated` 写入逐文件事件表，再完成运行状态。只记录已经成功完成 `_download_entry` 的文件，不记录跳过、删除或失败文件。

数据库层提供批量写入方法并在单个事务中提交，避免逐文件提交造成额外开销。若逐文件记录写入失败，则本次运行按失败处理，避免任务显示成功但缺少应有审计记录。

### 3. 在 `TaskState` 暴露 `run_id`，但不持久化进程内 task UUID

同步任务创建 `sync_runs` 后更新其内存 `TaskState.run_id`。前端查看当前同步任务文件时使用 `run_id` 调用与同步历史相同的查询接口。任务尚在排队、尚未创建运行记录或还没有成功落地文件时，查看入口不可用。

该方案避免为短生命周期的 task UUID 修改 `sync_runs`，同时让任务和历史使用同一持久化标识。服务重启后进程内任务本就不会保留，而同步运行及文件事件仍可从历史查询。

### 4. 当前任务过滤在后端完成

`TaskManager.list_tasks()` 仅返回状态为 `queued` 或 `running` 的任务；完成和失败的同步任务由 `sync_runs` 历史承载。前端仍基于接口结果渲染，不自行过滤，确保 API 语义与页面一致。非同步类完成任务不进入同步历史，完成后也从当前任务消失，符合“当前任务只显示正在运行任务”的要求。

### 5. 使用受控排序参数的只读查询接口

新增按映射和按运行查询文件的接口，要求调用者分别具备“同步映射”或“任务中心”页面权限。接口仅接受白名单排序字段 `file_name`、`synced_at` 和方向 `asc`、`desc`，数据库层通过枚举映射到固定 SQL 片段，禁止把原始参数拼入 SQL。

接口返回相对路径/文件名、动作和 Unix 时间戳，不返回可用于浏览任意文件系统的绝对本地路径。前端弹窗以文件名和同步时间为可点击表头，切换升降序；相对路径用于区分同名文件。

### 6. 统一复用一个文件列表弹窗

Vue 维护单一弹窗状态，包括标题、来源类型/ID、文件列表、排序字段、排序方向和加载/空状态。同步映射“查看”、当前同步任务“查看”和同步历史“查看”共用同一加载与排序逻辑。只有关联运行存在至少一条逐文件事件时，任务和历史显示查看操作；映射始终显示“查看”，没有记录时展示明确空状态。

## Risks / Trade-offs

- [逐文件事件表会随同步次数增长] → 为常用过滤和排序字段建立索引，查询映射时去重；后续如数据量显著增长再引入可配置保留策略，本次不自动删除审计数据。
- [同步完成与事件写入之间发生进程中断] → 批量事件写入和运行状态更新尽量置于连续事务边界；重启后未完成运行仍可识别为非成功状态。
- [旧同步运行没有逐文件信息] → API 返回空列表，前端显示“暂无文件记录”，不推断或伪造历史。
- [同名文件位于不同目录时仅看文件名会混淆] → 接口同时返回相对路径，弹窗展示路径辅助区分，文件名排序以文件名为主并以路径作为稳定次序。
- [运行中的文件清单会逐渐变化] → 逐文件事件在同步结果完成后批量写入，因此运行中任务通常在完成前不显示查看入口；这是用一致性换取实时性的明确取舍。

## Migration Plan

1. 通过现有 `_init_schema` 幂等创建 `sync_file_events` 表和索引，不修改或删除已有表与数据。
2. 部署后新同步运行开始生成逐文件事件；既有映射和历史记录保持可用，文件弹窗对旧数据展示空状态。
3. 发布后验证数据库迁移、同步成功/失败、当前任务过滤、三类查看入口和排序行为。
4. 回滚应用代码时保留新增表；旧版本会忽略该表。若未来确认不再需要，可在单独、经审批的数据迁移中清理。
