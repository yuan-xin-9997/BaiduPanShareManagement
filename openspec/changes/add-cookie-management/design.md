## Context

当前 Web 服务从 `data/secrets.json` 或 `BDPAN_COOKIE` 读取一份全局 Cookie，并在分享索引、目录浏览和同步任务中统一创建 `BaiduPanClient`。分享链接表没有凭据外键，系统配置页也只支持覆盖保存一份 Cookie。该变更横跨凭据存储、SQLite 数据模型、后台任务、API 与 Vue 页面，同时必须保证 Cookie 原文不进入浏览器响应、日志或 Git。

## Goals / Non-Goals

**Goals:**

- 支持多条具名 Cookie 的安全增删改查、状态展示和人工校验。
- 每条分享链接明确关联一条 Cookie，所有该链接衍生的索引、浏览和同步操作使用同一凭据。
- 以幂等方式迁移现有单 Cookie 和分享链接，升级期间不中断既有数据。
- 将添加时间、最近校验时间和有效状态按北京时间提供给管理界面。
- 保持 FastAPI、Vue 3、SQLite 与现有后台任务架构，不引入新的外部服务。

**Non-Goals:**

- 不自动登录百度账号、不采集用户名密码，也不自动从浏览器提取 Cookie。
- 不实现 Cookie 在不同分享链接间的自动轮换、负载均衡或失败后自动切换。
- 不把 Cookie 有效性视为永久结论；状态仅反映最近一次可判定的校验或请求结果。
- 不改变系统现有页面级权限模型，也不新增独立的 Cookie 权限粒度。

## Decisions

### 1. 元数据存 SQLite，敏感值保留在 secrets 文件

新增 `baidu_cookies` 表保存稳定 ID、名称、创建/更新时间、最近校验时间、状态和脱敏摘要；`data/secrets.json` 保存以 Cookie ID 为键的原文。写入 secrets 文件采用临时文件加原子替换，API 只返回脱敏摘要。这样沿用项目现有敏感信息边界，同时让查询、关联与迁移保持关系型一致性。

备选方案是把 Cookie 原文直接放入 SQLite，但当前项目没有数据库字段加密或密钥管理能力，会扩大数据库备份泄露的影响范围；另一个方案是让每条 Cookie 使用独立文件，会增加部署与原子更新复杂度。

### 2. 分享链接使用可空外键完成兼容迁移，业务层要求新记录必选

为 `share_links` 增加 `cookie_id` 外键并建立索引。迁移时，如果存在旧 `secrets.json.cookie`，创建名为“默认 Cookie”的记录并将所有空关联指向它；如果只有 `BDPAN_COOKIE`，运行时将其作为只读兼容默认凭据展示，但不把环境变量秘密复制到磁盘。新建或编辑分享链接时必须提交有效的 Cookie ID。删除仍被分享链接引用的 Cookie 返回冲突错误，要求管理员先重新关联，避免隐式切换账号。

备选的级联置空会使后续任务在运行时才失败；级联删除分享链接风险更高，均不采用。

### 3. 统一通过按分享链接解析的客户端工厂取 Cookie

Web 请求和 `TaskManager` 不再调用全局无参 `cookie_getter`，而是传入分享链接或 Cookie ID，通过凭据仓储读取对应秘密并构建 `BaiduPanClient`。刷新、目录浏览、下载和自动同步均复用该入口，避免部分路径遗漏关联关系。客户端运行中若更新了 `BDCLND` 等 Cookie 字段，可经仓储写回同一 Cookie ID。

### 4. 有效性状态采用三态并区分认证失败与暂时故障

状态定义为 `unknown`、`valid`、`invalid`。新增或修改 Cookie 后状态为 `unknown`；人工校验或真实业务请求获得明确成功后标记 `valid`，获得明确认证失效响应后标记 `invalid`。网络超时、百度风控或无法确定身份的响应不覆盖为 `invalid`，只记录校验时间与可安全展示的错误信息。此设计避免把服务器环境下常见的 `errno=-6` 风控误判为凭据必然失效。

### 5. Cookie 管理沿用系统配置页面权限

具备“系统配置”页面权限的用户可查看 Cookie 元数据；新增、修改、删除和校验操作仅允许管理员。分享链接页面用户只获取 Cookie ID、名称和状态的可选项，不接收摘要以外的敏感信息。所有错误、任务消息和日志对 Cookie 值及常见敏感字段进行清理。

## Risks / Trade-offs

- [SQLite 元数据与 secrets 文件无法组成单一事务] → 先原子写秘密、再提交数据库，并在启动时执行孤儿项清理/告警；删除操作先验证引用再更新两处。
- [百度接口风控导致有效性误判] → 使用三态模型，仅在明确认证错误时标记无效，暂时错误保持原状态并展示安全错误摘要。
- [运行中的任务遇到 Cookie 被修改] → 每个任务启动时读取一次凭据形成快照；修改只影响新任务，避免同一任务中途换账号。
- [Cookie 名称重复导致选择错误] → 数据库对规范化名称设置唯一约束，界面同时展示状态和添加时间。
- [删除或重关联影响后台任务] → 被引用的 Cookie 禁止删除；任务在入队和执行前都校验关联存在。

## Migration Plan

1. 应用启动时幂等创建 `baidu_cookies` 表、索引，并为 `share_links` 增加可空 `cookie_id`。
2. 若旧 `secrets.json.cookie` 存在且尚未迁移，创建“默认 Cookie”，把原文移动到按 ID 存储的映射，并关联所有现有分享链接；迁移完成后移除旧键。
3. 若仅配置 `BDPAN_COOKIE`，保留只读兼容路径；管理员需要在页面添加持久 Cookie 后才能新增分享链接，并可将旧链接改绑。
4. 部署后运行数据库迁移、后端测试、前端构建与 API 冒烟测试，再通过 Jenkins 手工构建发布。
5. 回滚时保留新增表、字段和 secrets 映射；旧版本无法识别多 Cookie，因此回滚前需将选定凭据同步回旧 `cookie` 键。回滚过程不得删除新增元数据。

## Open Questions

无。默认采用“被引用时禁止删除”和“三态有效性”策略，实施中如百度校验接口表现与现有客户端测试不符，再以不误判失效为原则调整探测方式。
